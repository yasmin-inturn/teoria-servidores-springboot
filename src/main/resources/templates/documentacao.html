Como pensar nisso: um restaurante

O projeto é separado em duas pastas (catalogo/ e doc/), e dentro de catalogo/ cada classe tem um papel só - igual a um restaurante dividido entre salão e cozinha. Pensar assim ajuda a entender uma requisição HTTP antes mesmo de ler o código:

No restaurante No servidor
O cliente quem chama a API (navegador, curl, um app)
O pedido feito ao garçom a requisição HTTP - ex.: GET /api/produtos/3
O garçom (anota, confere e leva à cozinha) @RestController - o ProdutoController
A cozinha (onde o prato é de fato preparado) @Service - o ProdutoService
"Esse prato não está no cardápio" produto inexistente -> 404 Not Found
Garçom recusa um pedido mal preenchido, sem nem levar à cozinha Bean Validation rejeita o JSON -> 400 Bad Request
O prato pronto, entregue de volta à mesa a resposta HTTP em JSON

Na prática: o cliente faz o pedido (GET /api/produtos/3) → o garçom (ProdutoController) confere se o número 3 faz sentido e chama a cozinha (ProdutoService.buscar(3)) → a cozinha encontra o produto (ou não, e aí vira 404) → o prato volta pronto como JSON. Nenhum cliente fala direto com a cozinha, e é exatamente essa separação de responsabilidades (controller ≠ service) que torna o código fácil de testar e de localizar.
